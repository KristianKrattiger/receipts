# Receipts Density Plan — substantive headlines

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or
> superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce ledgers thick enough that a reader meets three or four load-bearing rows before
they stop scrolling, and at least one row per subject that is quotable on its own.

**The constraint is not source count.** Measured across the three committed reports:

| report | claimant chars | independent chars | proposed | admitted |
|---|---|---|---|---|
| tesla-fsd | 4,232 (1 doc) | 373,954 (6 docs) | 8 | 4 |
| vercel | 17,143 (3 docs) | 32,719 (2 docs) | 9 | 2 |
| claude | 15,246 (3 docs) | 72,626 (3 docs) | 9 | 2 |

Three corpora differing by two orders of magnitude in size, and all three propose 8–9. One model
call is the ceiling. Vercel has a healthy 1:2 claimant/independent ratio and still yields two rows;
Tesla has a catastrophic 1:88 ratio and yields four. **Corpus size is not what is binding — the
single proposal pass is.** Adding twelve sources to one call makes each source's chunks compete for
the same 40–80 candidate slots and would likely make the ledgers *worse*.

Second finding: of 18 denials, 13 are `LOW_CONFIDENCE`, and the values cluster hard —
`{0.45: 6, 0.4: 3, 0.35: 2, 0.42: 1, 0.3: 1}`. Six proposals sit at exactly 0.45, one hundredth
under the floor. The prompt never defines what the number measures, so the model is emitting a
hedge, not a calibrated probability. That is a prompt defect being read as a quality signal.

**Order matters.** Tasks 1–3 raise yield from the corpus already committed and are verifiable
offline against fixtures for free. Only then is it worth spending on new sources (Tasks 4–6),
because until the ceiling moves, better sources cannot show up in the output.

## Global Constraints

- Constants today: `MAX_QUOTE_WORDS = 40`, `CONFIDENCE_FLOOR = 0.5`, `DIVERGENCE_IDF_FLOOR = 0.13`,
  `perDoc = 8`, `total = 40`. Any change to these lands with the measurement that justified it.
- `doc.text` is normalized once in `fetch/` and immutable thereafter. Nothing added here may
  transform it before anchoring.
- Every tuning decision is made against **the committed fixtures**, re-analysed with
  `--from-fixture`, so the corpus is byte-identical and the engine is the only variable.
- ~~**No captcha solving, and no defeating bot detection.**~~ **REVERSED 2026-09-05.** Captcha
  solving is enabled; `webBotAuth` turned out not to exist on this platform (`400`, see
  `reports/egress-2026-09-05.json`), so the "defensible alternative" this constraint pointed at
  was never available. The original text is kept below because the reasoning still governs how
  the reversal has to be presented.

  > A source that refuses is a `not read` row, and that column is a feature of this tool, not a
  > gap in it — a ledger that reports its own blind spots is the entire pitch. Coverage grows by
  > finding independent sources that are readable, not by defeating the ones that are not.
  > `webBotAuth` is in scope precisely because it is the opposite: signed, identified requests to
  > a directory the site can verify.

  What the measurement changed: the constraint was written believing Reddit and G2 refused us on
  the merits. Neither claim survived. Reddit was refusing an *unproxied datacenter IP* — behind
  `us:static` it answers `200` and presents a human-verification challenge — and G2 returns a
  bare `403` with no challenge at all. The constraint was declining a remedy for a condition that
  had never been diagnosed.

  **What does not change:** the `not read` column stays, and it stays honest. A source that
  cannot be read after this still reports why, and the README states plainly that this tool
  solves challenges. The pitch was never "we are locked out"; it was "we tell you exactly what
  we could and could not read", and that survives the reversal intact. What would break it is
  reading a source and not saying how.
- Commit after every task. Never `--no-verify`.

### Task 1: Fan the proposal pass — the ceiling fix

One call sees the whole corpus and returns ~8 proposals. Six independent documents against a
claimant corpus is six *separate* comparison problems, and collapsing them into one prompt makes the
model triage rather than enumerate.

**Files:** `src/cartographer/propose.ts`, `src/pipeline.ts`, tests

- [x] `proposeRelations` gains a per-independent-document mode: for each independent doc, one call
      carrying the full claimant candidate set plus that document's candidates only.
- [x] Claimant-vs-claimant self-contradiction is its own pass (all claimant docs, no independent),
      since `admit` already supports both sides sharing a role and a vendor contradicting its own
      docs is the most damning row available.
- [x] **Namespace `proposalId` per pass** (`d3-p0`, not `p0`). Today ids are assigned `p${i}` per
      call; merging passes without namespacing silently collides them, and the audit trail — the
      thing that makes the guarantee checkable — is what breaks.
- [x] Run passes with bounded concurrency (default 3, matching the browser fan). Surface per-pass
      failures rather than failing the run: one refused pass is a partial ledger, not no ledger.
- [x] `admit` needs no change — the pair key and claim key already dedup across passes, and cross-
      pass duplicates are now the *expected* case rather than a rarity.
- [x] Report the pass count and total proposals in the audit line.
- [x] Tests: stub client asserts N calls for N independent docs; ids unique across passes; a pass
      that throws does not lose the others; duplicate proposals from two passes collapse to one row.

**Expected:** ~8 proposals per pass × 6 passes ≈ 45–50 proposals on Tesla, against 8 today.

**Result (2026-09-04), Tesla, same fixture, `--candidates 80`:**

| | before | after |
|---|---|---|
| passes | 1 | 7 |
| proposed | 8 | 30 |
| admitted | 4 | 13 |
| rows | 3 divergent, 1 corroborated, 0 unverified | 7 divergent, 4 corroborated, 2 unverified |

**The fan exposed a correctness bug on its first run, now fixed.** With one independent source per
pass, `unsupported` — "no excerpt corroborates this" — became a judgement no pass had the evidence
to make. The first fanned ledger reported the Tesla subscription price as `unverified` from one pass
and `corroborated` from another, in the same report. Fixed at both ends, as with every other gate
here: `planPasses` now emits a dedicated whole-corpus `unsupported` pass and tells the relational
passes not to attempt it, and `admit` retires an unsupported claim whose span already carries a
relation, judging relations first so proposal order cannot decide the outcome.

**Still open after this task:** near-duplicate rows. Two passes can anchor slightly different
claimant spans on the same underlying claim, and span-keyed dedup cannot see that they are the same
finding. Tesla rows 6 and 7 overlap this way. Not addressed here; revisit after Task 2, since
tighter confidence may retire the weaker of each pair on its own.

**Reports regenerated:** Tesla only. `vercel.json` and `claude.json` still predate the fan and will
be regenerated in Task 7, once Tasks 2 and 3 have settled — re-running them now would pay twice for
output the next two tasks are designed to change.

**Cost:** linear in independent docs, but each call is much smaller. Measure actual spend on the
first Tesla run and record it before rolling out to other subjects.

### Task 2: Define what `confidence` measures

Six proposals at exactly 0.45 is not six borderline findings, it is an undefined scale.

**Files:** `src/cartographer/propose.ts` (prompt), `src/bookkeeper/admit.ts` (only if measured)

- [x] Prompt defines the quantity: *confidence is how certain you are that the two quotes, as
      written, stand in the stated relation — not how likely the underlying claim is to be true, and
      not how important it is.* An exactly-quoted flat contradiction is 0.9+, even on a small point.
- [x] Instruct use of the full range and forbid the hedge band: if a proposal is worth making, it is
      above 0.5 or it is not proposed.
- [x] Re-run the fixtures, diff the histogram against Task 0's baseline.
- [x] **Only then** decide whether `CONFIDENCE_FLOOR` moves. If the cluster disperses, the floor was
      never the problem and stays at 0.5. Lowering the floor first would admit exactly the rows the
      floor exists to stop.

**Result (2026-09-04), Tesla, same fixture.** The cluster dispersed:

```
before   0.36×1 0.40×2 0.42×1 0.45×2                    (6 values, 3 distinct, 2 at the top)
after    0.33 0.34 0.35 0.38 0.40 0.42 0.44 0.45×2      (9 values, 8 distinct)
```

Every value now falls *below* 0.45 except two, and eight of nine are distinct. The model was
hedging on an undefined scale, exactly as suspected — given anchors it produces graded judgements
instead. Rows rose 13 → 14 and, more usefully, spread across all three statuses (5 divergent,
6 corroborated, 3 unverified) rather than piling into divergent.

**`CONFIDENCE_FLOOR` stays at 0.5.** The cluster was never the floor's fault, and the dispersed
distribution shows the rejected proposals really are the weak ones. Lowering it now would admit
0.44-grade inference, which is what the floor is for.

Note the removed line as much as the added ones: the prompt used to say *"low-confidence proposals
are filtered out"*, which tells the model its output is being gated and invites it to aim at the
gate rather than report what it believes. The new prompt never mentions the floor.

### Task 3: Stop starving the claimant side

Every relation needs a claimant `from`. Tesla's claimant corpus is 1.1% of its total, so round-robin
selection gives the vendor's own words a handful of slots and the ledger is capped by that, not by
how much Wikipedia was read.

**Files:** `src/retrieve/select.ts`, tests

- [x] Reserve a floor share of candidate slots for claimant-role documents (target 40%), filled from
      claimant docs' ranked chunks, with unused reservation released back to the general pool so a
      claimant-thin corpus is not penalised twice.
- [x] Keep round-robin *within* each role — the existing comment explains why a global score sort
      evicts independent sources, and that reasoning is unchanged.
- [x] Tests: a 1-claimant/6-independent corpus gives the claimant ≥40% of slots; a corpus with no
      claimant chunks does not deadlock; existing round-robin tests still pass.

**Result (2026-09-04), measured offline against the committed fixtures at `--candidates 80`:**

| corpus | claimant slots before | after |
|---|---|---|
| tesla-fsd | 12/79 (15%) | **30/80 (38%)** |
| vercel | 37/69 (54%) | 37/69 — unchanged |
| claude | 40/80 (50%) | 38/80 — unchanged |

It behaves as a floor rather than a quota: only the starved corpus moves, and the two already above
the share are untouched.

**A second bug, found by the test rather than by reasoning.** The per-document cap and the
reservation fought, and the cap won silently. The cap exists to stop one document dominating its
side — but a corpus with a single claimant page has a claimant side of *one document*, where the cap
restrains nothing and merely leaves the reservation unfillable. Tesla is exactly that: one vendor
page, a cap of 12, and a reservation of 32 that could never draw more than 12. The claimant side now
raises its own cap to whatever the reservation needs; the independent side keeps the original cap,
so no single independent document can crowd out the others.

**Still unverified:** whether this improves the *claimant docs cited* figure the harness surfaced
(Claude 1/3, Vercel 2/3). That needs a real run — blocked on API credit, see below.

### Task 4: Source plans that generate headlines

Reddit and G2 were the intended "where users complain" and both refuse. The readable equivalents
are better sources anyway, because they are specific and dated.

**The row that reads as a headline** pairs a *specific, quantified vendor promise* against a
*specific, dated independent measurement*. "Requires human intervention every 13 miles" works
because both halves are concrete. Marketing adjectives against forum grumbling never will.

Source classes to add, in descending order of expected yield:

- [x] **The vendor's own regulatory filings.** For a public company, the 10-K risk factors are the
      same company's lawyers contradicting its own marketing, in writing, under penalty. Tesla's
      filings describe FSD as requiring active supervision and disclose NHTSA investigations while
      `tesla.com/fsd` says it "will drive you almost anywhere". `sec.gov` EDGAR is plain HTML and
      does not refuse browsers. **This is the single highest-value source class in the plan** — mark
      the filing `claimant` role, since it is the vendor's own words, and let the claimant-vs-
      claimant pass from Task 1 find the contradictions.
- [x] **Status page incident history**, not the current-status page — `status.x.com/history` carries
      months of dated postmortems against uptime marketing.
- [x] **GitHub issue search** on the vendor's own repo (`github.com/vercel/next.js/issues?q=...`).
      Readable, practitioner-written, specific, and it is genuinely where users complain.
- [x] **Regulator dockets**: `regulatorTargets` and its `Industry` lookup table shipped, but the
      table itself ships **empty**. Its one seeded entry, `nhtsa.gov/recalls?make=<subject>`,
      probed to a generic landing page — zero occurrences of "Tesla" in 8,452 characters
      (`fixtures/probe-source-classes.json`); the `make` parameter is silently ignored. The URL
      that does carry dated recall text, `api.nhtsa.gov/recalls/recallsByVehicle`, needs `make`
      **and** `model` **and** `modelYear` — `make` alone returns `Count:0`
      (`fixtures/probe-nhtsa-shapes.json`) — and two of those three cannot be derived from a
      company name, so it cannot live in a name-keyed table. It went into `plans/tesla-fsd.json`
      instead: 5,835 characters of dated recall summaries, verified on two model/year pairs. The
      `automotive` entry therefore stays empty, the way `webBotAuth` waited on a platform that
      genuinely signed requests. The mechanism itself is now wired and carrying a source:
      `--industry` on the CLI, an enum-declared argument on the MCP tool and `?industry=` on the
      web server all reach `buildSourcePlan`, and `fintech` holds the **CFPB complaint database**
      — name-derivable, unlike NHTSA. Probed 2026-09-06 (`fixtures/probe-cfpb.json`): 24,338
      characters, every complaint in the document filed against Chime Financial Inc.
      Three properties of that URL fail silently and are pinned by tests — the trailing slash
      (else the HTML page), no `format=json` (else 404), and no `sort=` (else date order discards
      relevance and returns complaints against Ally, Netspend and Wells Fargo).
      The same probe caught a seventh instance of this codebase's recurring defect: CFPB answers a
      no-match search with 365 characters of Elasticsearch envelope, past `MIN_USEFUL_CHARS` and
      matching no marker, so it would have been admitted as a source saying nothing. NHTSA's
      `Count:0` is the same fact in 66 characters, caught until now by the length floor alone.
      Both are matched structurally now.
- [x] **Independent measurement sites**: two landed, one did not. **Downdetector** joined
      `buildSourcePlan`'s templated defaults — every future subject gets it — after probing against
      Vercel and returning real subject-specific content ("User reports show no current problems
      with Vercel", plus a 24-hour report chart). **LMArena**'s leaderboard was hand-added to
      Claude's plan file: 41,500 characters, 88 mentions of Claude carrying comparative scores with
      confidence intervals — the independent counterweight a model card's claims never have.
      **Artificial Analysis**, the other benchmark-aggregator candidate, did not land: the guessed
      URL 404'd (`fixtures/probe-hand-research.json`), and a guessed URL that doesn't resolve is not
      a source, it's a claim about one.
- [x] Keep Reddit and G2 in the plans. They report as `not read` with a reason, and that is the
      honest statement of coverage.

Per-subject plan files, each with ≥4 claimant and ≥6 independent targets.

## Headline hypotheses to test

Written down in advance so a null result is visible as a null result rather than quietly dropped.

1. ~~**Tesla 10-K vs `tesla.com/fsd`**~~ — **NULL RESULT (2026-09-04).** The 10-K was fetched
   (385k chars, read first try) and produced eight rows. Zero of them pair two Tesla documents:
   the filing does not contradict the marketing page on any claim the gate would admit.

   What the ledger showed instead is sharper than the hypothesis. Split Tesla's rows by which of
   its own documents they cite: the **10-K produces 8 rows, all `CORROBORATED`**; the **Vehicle
   Safety Report produces 5 `DIVERGENT`**. The SEC filing agrees with Tesla's critics while the
   marketing page contradicts them — same company, two registers, visible only because both are
   in one ledger.
2. **Tesla FSD community disengagement telemetry** vs "minimal intervention". A stronger, sourced
   version of the current 13-mile row.
3. **Vercel status-page incident history** vs "secure by default" and any uptime language on
   `/pricing` — count of dated incidents in 90 days is a number a reader can hold.
4. **Anthropic status page Cowork failures** vs the Cowork product page. Already found in a thin
   form; more independent coverage should sharpen it.
5. **Any vendor whose GitHub issues contradict its docs' "supported" language** — the CLI-login row
   dropped at 0.45 was this shape and may survive Task 2's calibration.

## Definition of done

- A subject exists whose ledger carries **6+ admitted rows across at least two statuses**.
- At least one row is quotable standalone, with both halves specific and dated.
- Proposal count per run is 40+, not 8.
- The proxy table is re-measured and dated, with `webBotAuth` characterised.
- Every ledger produced by the runs above is committed, including the weak ones.
